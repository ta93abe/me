# トップページ刷新アイデア集

> 2026-09-06 / 発散用のデザインノート。採用案・公開原稿は未確定。
> ローカルの実装・設定をもとにした提案で、本番の表示や公開コンテンツ件数は未確認。

Takumi Abe / ta93abe の「データ基盤と CI を書く」「絵と音楽も置く」を、どんな入口にすると伝わるか。見た目の方向性を **16 案**、組み合わせられる小さなアイデアを **48 案**、コピーを **12 案**、ページ構成を **5 案**に分けて考える。

最初に比較するなら、**A02「設計図」・A03「コードと余白」・A05「文字のポスター」**。専門性、個人性、簡潔さのどれを中心に置くかが、はっきり異なる。

## 1. 今あるものと、刷新で考えたいこと

### 実装から確認できること

| 項目 | 現状 | 発想の起点 |
| --- | --- | --- |
| トップ | `HeroSection` に氏名・紹介・代表作 3 件・About / Blog / Contact を集約 | 短い入口としてまとめるか、下に読み進める構成にするか |
| 見た目 | 紙色、明朝体、紫と黄土、抽象的な WebGL 背景と CSS の代替背景 | 静けさを残す、技術の形を加える、雰囲気を大きく変える |
| 画面構造 | `lockViewport` を利用。外側を固定し、メイン領域で縦スクロールする構成 | 長いホームにする場合は通常のページスクロールも検討する |
| 代表作 | `dbt-jobs`、`dbt-intro`、`enbu` を設定で選定済み | 名前だけでなく、何に使うものか・何を考えたかを見せる |
| 公開導線 | About / Blog / Contact、Links / Tools / Slides、RSS、Substack | 読む・使う・知る・連絡する、という行動で整理できる |
| コンテンツ運用 | 公開本文は pubme → R2。ブログ一覧・詳細は R2 を読む | 新着を自動表示する案には取得・キャッシュ設計が必要 |
| 未公開の領域 | `/gallery` `/atelier` `/bookshelf` `/works` は `/` にリダイレクト | 作品が公開されるまでは、これらをトップの行き先にしない |
| 計測 | 代表作クリックとトップ CTA の PostHog イベントがある | 刷新後も入口から次の行動への変化を比較できる |

### 刷新で検証したい仮説

- 抽象背景の一部を作品・図・短い制作メモに変えると、人物像が具体的になるか。
- 代表作を「3 件均等」から「1 件を大きく、2 件を添える」にすると、読み始めやすくなるか。
- Blog へのボタンに記事の中身を少し添えると、次に読む理由が生まれるか。
- 技術と創作を同じページに置くとき、二分する方がよいか、一つの制作活動として混ぜる方がよいか。
- 毎週更新しなくても成立する構成と、近況を更新したくなる構成のどちらが本人に合うか。

以下は効果が確認された改善策ではなく、比較するための案。現状の良さである短さ・落ち着きも、残す選択肢に含める。

## 2. 大きなデザイン方向性：16 案

素材の区分は次のとおり。

- **既存中心**：現行の氏名・紹介・代表作・リンクを主材料にできる。
- **追加少量**：短い解説、図、写真などを少し用意すると成立する。
- **公開後**：絵・音楽・記事など、実際の公開素材が揃ってから効果が出る。

実装規模の「小・中・大」は案同士の相対比較。見積もり日数ではない。

### A01. 個人誌の表紙

- **第一画面**：左上に小さな `ta93abe`、中央に大きな氏名。下半分を「つくったもの」「書いたもの」の目次として組む。
- **見た目**：生成り、墨色、朱色を少量。明朝の大見出しと細い罫線、余白に小さな注釈。
- **固有の工夫**：代表作に `01 / 02 / 03` と短い編集コメントを添え、自分で選んだ目次にする。
- **続き**：代表作 → 読んでほしい記事 → 小さな自己紹介 → Contact。
- **モバイル**：表紙の文字組みを残し、目次は縦一列。冊子をめくる操作は要求しない。
- **素材・負担**：既存中心 / 実装小 / 更新低。記事が少なくても、代表作の目次だけで成立する。
- **注意点**：現在の紙・明朝の延長線。大きな変化が欲しい場合は、背景より情報の組み方を大胆に変える。

### A02. データ基盤の設計図

- **第一画面**：左に氏名と紹介、右に大きな関係図。`入力 → 変換 → テスト → 配信` の流れに作品への入口を置く。
- **見た目**：淡い青灰色の紙、濃紺の線、オレンジの小さな注記。方眼は図の周辺に限定する。
- **固有の工夫**：`dbt-jobs` は CI、`dbt-intro` は学習・モデル、`enbu` は基盤の入口として配置する。図は活動の概念図と明記し、実システムの構成と混同させない。
- **続き**：図で選んだ作品の概要 → 関連する文章 → 道具。
- **モバイル**：図を「入力・変換・検証」の縦の流れに変え、各作品を通常のリンクでも読めるようにする。
- **素材・負担**：追加少量 / 実装中 / 更新低。作品の用途を整理した図が 1 枚あれば始められる。
- **注意点**：初見の人にも意味が分かる日本語を添える。図を動かさなくても目的地に到達できる構成にする。

### A03. コードと余白

- **第一画面**：画面の約 3 分の 2 に整然とした紹介と作品リスト。残りに、一本の手描き線や抽象的な色面を大きく置く。
- **見た目**：白、黒、絵から選んだ一色。コード側は整列、創作側は自由な配置にする。
- **固有の工夫**：細い直線が途中から手描き線に変わる。技術と創作を一つの形でつなぐ。
- **続き**：「つくる」の中にコードと、公開後の絵・音を並べる。職業と趣味で別人格のように分けない。
- **モバイル**：紹介 → 線や色面 → 代表作の順。左右切り替え式にはしない。
- **素材・負担**：追加少量 / 実装中 / 更新低。本人の線画があれば強い。初期は装飾図形として作り、本人の作品とは表記しない。
- **注意点**：絵・音楽の未公開ページへのリンクは置かない。作品公開までは、趣味の一文と装飾だけでもよい。

### A04. 作業机をのぞく

- **第一画面**：俯瞰の机に、コードのメモ、名刺、制作ノートを配置。名刺の位置に氏名と紹介を固定する。
- **見た目**：木や紙を連想する淡い色、重なる紙片、付箋一色。実写でも平面イラストでも成立する。
- **固有の工夫**：プロジェクトを「机に広げている資料」として表現し、クリックすると対応する公開先へ進む。
- **続き**：机の下から普通の縦リストが続き、代表作と文章を落ち着いて読める。
- **モバイル**：紙片の重なりを解き、同じ順番の一覧にする。
- **素材・負担**：追加少量 / 実装中〜大 / 更新中。机の写真または専用イラストが必要。
- **注意点**：ドラッグを前提にしない。背景の演出と押せるものを明確に分ける。

### A05. 文字のポスター

- **第一画面**：画面幅いっぱいに `TAKUMI ABE`。その下に短い日本語の紹介、代表作 3 件、主要リンクを置く。
- **見た目**：白黒と強い一色。大きな欧文、細い和文、思い切った改行。背景画像はなくてもよい。
- **固有の工夫**：名前の字間や一文字の形に特徴を持たせ、サイト全体の署名として使う。
- **続き**：一画面の短い入口で完結するか、すぐ下に代表作を一つだけ詳しく置く。
- **モバイル**：名前を二行にして同じ迫力を出す。文字の切れや横スクロールを避ける。
- **素材・負担**：既存中心 / 実装小 / 更新低。新しい作品素材を待たずに比較しやすい。
- **注意点**：名前だけで画面を埋めず、何をする人かと次の行動を一緒に見せる。

### A06. 手入れする庭

- **第一画面**：紹介の下に「育てているもの」を三つ。代表作、考えているテーマ、公開済みの文章を静かに並べる。
- **見た目**：苔色、クリーム色、土色。植物の絵を多用するより、枝分かれする線と余白で庭を感じさせる。
- **固有の工夫**：完成・未完成を競う表示ではなく、「試す」「整える」「書き残す」など制作の状態を本人の言葉で示す。
- **続き**：関心のテーマ → 作品や記事 → 更新した日付。
- **モバイル**：枝分かれをほどき、テーマごとの短い段落にする。
- **素材・負担**：追加少量 / 実装中 / 更新中〜高。近況を継続して書く習慣と相性がよい。
- **注意点**：今の状態を手入れしないと古く見える。更新頻度を約束せず、最終更新日を実データで示す。

### A07. 個人のリリースノート

- **第一画面**：小さめのプロフィールと、日付付きの「公開した・直した・書いた」の一覧。
- **見た目**：等幅の小さな日付、読みやすい本文、一本の縦線。新しい項目だけにアクセント色を使う。
- **固有の工夫**：コード、記事、登壇、公開後の作品を、成果物の種類を添えた一つの時系列で見せる。
- **続き**：最近の記録 → 固定の代表作 → About。
- **モバイル**：日付を各項目の上に置き、長いタイトルも自然に折り返す。
- **素材・負担**：公開後 / 実装中 / 更新中〜高。履歴と日付のまとまったデータが必要。
- **注意点**：GitHub のコミット数だけで活動を表さない。何も公開していない日を空欄で可視化しない。

### A08. 一点を展示する

- **第一画面**：代表作を一つ大きく展示し、余白に氏名・用途・制作メモを置く。現状なら `dbt-jobs` の説明図でも成立する。
- **見た目**：美術館の壁のような白、細いキャプション、広い余白。画像の色が主役になる。
- **固有の工夫**：コードにも「展示物＋解説札」という形式を使い、何を解決するものかを鑑賞できる形にする。
- **続き**：他の代表作 2 件 → 関連する文章 → 自己紹介。
- **モバイル**：作品、タイトル、説明の順。図の文字が縮みすぎる場合は、本文に内容を移す。
- **素材・負担**：追加少量 / 実装中 / 更新低〜中。十分な大きさで見せられる図や画像が必要。
- **注意点**：自動カルーセルで主役を切り替えない。何を展示するかを自分で選ぶ。

### A09. フィールドノート

- **第一画面**：大きな見出しと、公開可能な図・短い観察メモ・代表作への索引。ノートの見開きのように配置する。
- **見た目**：薄い罫線、余白の注釈、小さな番号。完成原稿は活字、本人の手書き素材はアクセントにする。
- **固有の工夫**：完成品の説明に加え、「どこで迷ったか」を一つ添える。思考の過程を入口にする。
- **続き**：観察 → 試作 → まとまった文章、という順に読む。
- **モバイル**：欄外の注釈を本文の直後へ移す。
- **素材・負担**：公開後 / 実装中 / 更新中。公開できる制作メモがあると強い。
- **注意点**：架空の制作過程やノートを実物として出さない。長いメモはブログ側に置く。

### A10. 夜の作業場

- **第一画面**：濃い背景に明るい氏名、机の灯りのような限定的な光。代表作は「今開いている作業」として並べる。
- **見た目**：炭色、温白色、銅色。黒地の全面発光や装飾的な数値は控え、文章を読みやすくする。
- **固有の工夫**：技術の図と音の波形を同じ細い線で描き、制作する時間の雰囲気を揃える。
- **続き**：代表作 → 文章 → 道具 → 連絡。
- **モバイル**：背景を静止させても同じ雰囲気が残るよう、明暗と文字組みで作る。
- **素材・負担**：既存中心 / 実装中 / 更新低。波形を装飾に使う場合は、公開曲の存在を示す UI にしない。
- **注意点**：ダーク化だけで終わらせず、光の位置と余白に一貫した意図を持たせる。

### A11. よくできたプレーンテキスト

- **第一画面**：氏名、紹介、三つの代表作、数本のリンク。色も装飾もごく少なく、文章の順序で伝える。
- **見た目**：一段組、気持ちのよい行間、控えめなリンク色。等幅は番号や補助情報に絞ってもよい。
- **固有の工夫**：各リンクに「何がある場所か」を一文添える。短い README のような入口にする。
- **続き**：スクロール量を増やさず、About や Blog に深さを任せる。
- **モバイル**：ほぼ同じレイアウトで読める。
- **素材・負担**：既存中心 / 実装小 / 更新低。
- **注意点**：仮実装に見えないよう、文字サイズ、段落間隔、リンクの文言を丁寧に詰める。

### A12. 関心の地図

- **第一画面**：氏名の周囲に「データ基盤」「CI」「書くこと」、公開後に「絵」「音」を配置。公開コンテンツを線で結ぶ。
- **見た目**：地図のような小さなラベルと線、控えめな色分け。空間の広さを余白で表す。
- **固有の工夫**：記事とコードなど、種類をまたぐ関係を見せる。「この文章からこの道具が生まれた」が辿れる。
- **続き**：選んだテーマの項目を近くに表示し、通常の一覧も用意する。
- **モバイル**：最初からテーマ別の縦リストを表示する。
- **素材・負担**：公開後 / 実装大 / 更新中〜高。結びつけられる素材と関係データが必要。
- **注意点**：項目が少ないうちは大げさになりやすい。自由に動くノードや操作説明を必須にしない。

### A13. 切り抜きのコラージュ

- **第一画面**：氏名の周囲に、実際の図、作品の切り抜き、登壇資料の一部を非対称に配置する。
- **見た目**：紙片、太い文字、二色の印刷を思わせる配色。画像ごとの縁や注釈で秩序を作る。
- **固有の工夫**：形式が違う制作物を、一人の「つくったもの」として混ぜる。
- **続き**：気になった切り抜きから各公開先へ。下には整った作品一覧を置く。
- **モバイル**：重なりを減らし、縦に流れる小さな展示にする。
- **素材・負担**：公開後 / 実装中〜大 / 更新中。実素材が複数必要。
- **注意点**：文字を画像内に閉じ込めない。装飾が見出しやリンクを隠さないようにする。

### A14. 一つの風景に署名する

- **第一画面**：本人が用意した写真や絵を大きく見せ、余白に氏名と紹介を置く。下端に代表作の入口を添える。
- **見た目**：画像から色を取り、UI の主張を抑える。余白に水平線を一本だけ引く。
- **固有の工夫**：背景を個人の選んだ一枚にすることで、その人の感覚が残る入口にする。
- **続き**：風景のすぐ下に技術の代表作を配置し、専門性につなげる。
- **モバイル**：画像を上下に切りすぎず、必要なら縦向けの別トリミングを作る。
- **素材・負担**：追加少量 / 実装小〜中 / 更新低。大きく使える本人の写真・作品が必要。
- **注意点**：文字の読みやすさを画像任せにしない。素材がなければ他案を先に試す。

### A15. 個人サイトの遊びを戻す

- **第一画面**：小さな紹介、オリジナルのバッジ、短いリンク集。「ここに来た」感覚のあるコンパクトなホーム。
- **見た目**：限られた色、ピクセル風の小物、素朴な枠線。本文は通常の読みやすい書体を使う。
- **固有の工夫**：プロフィールやコードへ進む小さな絵ボタンを、自分のアイコンとして育てる。
- **続き**：代表作 → お気に入りの道具 → 公開先。隅に押して遊べる小さな仕掛けを一つ。
- **モバイル**：バッジを折り返し、リンクの押せる面積を十分に取る。
- **素材・負担**：追加少量 / 実装中 / 更新低。小さなオリジナル素材があるとよい。
- **注意点**：偽の訪問者数、点滅文字、音の自動再生は使わない。レトロさは造形で出す。

### A16. 一通の短い手紙

- **第一画面**：「こんにちは、Takumi Abe です。」から始まる数行の紹介。文中に代表作・文章・連絡先へのリンクを埋め込む。
- **見た目**：狭めの本文幅、広い外側の余白、署名。リンクは控えめな下線で示す。
- **固有の工夫**：ナビゲーションの選択肢を並べる前に、本人の言葉で何をしているかを話す。
- **続き**：追伸に代表作一覧や最近書いたものを添える。
- **モバイル**：そのまま短い文章として読める。文字を小さくして一画面に押し込まない。
- **素材・負担**：追加少量 / 実装小 / 更新低〜中。自分の言葉の紹介文を用意したい。
- **注意点**：文中リンクだけでは探しにくいため、About / Blog / Contact の通常の導線も残す。

## 3. 方向性の比較

記憶に残りやすさや更新負担は設計上の見立て。訪問者の反応を測った結果ではない。

| A02 設計図 | 技術・関係 | 図 1 枚 | 中 | 低 | データ基盤と CI の専門性を見せる |
| A03 コードと余白 | 技術と創作の共存 | 線画または装飾 | 中 | 低 | 本人らしい両面を一つにする |
| A04 作業机 | 人柄・制作環境 | 写真またはイラスト | 中〜大 | 中 | 遊びと温度感を出す |
| A05 ポスター | 名前・文字 | 既存中心 | 小 | 低 | 少ない情報で印象を変える |
| A06 庭 | 継続・関心 | 近況の短文 | 中 | 中〜高 | 育てるサイトにする |

## 7. 少ない素材でも成立させるルール

| 状態 | トップでの扱い |
| --- | --- |
| ブログ記事 0 件 | 新着欄を省略。代表作と既存の Blog 導線だけで構成する |
| ブログ記事 1 件 | 一つの記事として紹介する。3 枠を埋めるためのダミーを作らない |
| 記事が増えた | 新着は最大 3 件、必要ならおすすめを別に選ぶ |
| 絵・音楽が未公開 | 紹介文で関心を伝える。公開ページを装った空のギャラリーは置かない |
| 作品を公開できた | 公開先が用意できたことを確認してから、画像や再生導線を追加する |
| 近況更新が止まった | 実際の更新日が分かる記録として残すか、近況欄を外す |
| 外部データを取得できない | 確認済みのキャッシュがあれば使い、なければ欄を省く。基本の紹介・代表作・ナビは表示する |

Now、最近の活動、制作途中の紹介は、継続更新したいものだけ選ぶ。代表作を自分で選ぶ構成なら、更新頻度が低くても意味が残る。

## 8. 実装に進むときのメモ

ここはアイデアを実装案に変えるための確認事項。今回の作業範囲はこの文書の作成まで。

### レイアウトと見た目

- 長いホームを選ぶ場合、トップの `lockViewport` と固定フッターを見直し、通常の縦スクロールで構成する案を試す。
- 全ページ共通の明朝体や色を変える前に、トップに限定して比較する。採用後に下層ページへ広げる範囲を決める。
- 書体は数を増やす前に、今ある書体のサイズ・太さ・行間で比較する。新しく追加する場合は必要なウェイトと文字範囲に絞る。
- 図・画像・色は、専門性や個人性を説明する役割を与える。大きな背景を使う場合も、説明文と主なリンクの読みやすさを確保する。

### データと公開

- 現行の `SITE`、`FEATURED_WORKS`、`HOME_CTAS` を出発点にする。代表作の説明をトップと About で別々に管理しない。
- ブログ本文・制作ノート・公開作品の原稿は、既存の pubme → R2 の運用に従う。この設計メモは公開本文の置き場ではない。
- 新着ブログを表示する場合、`listBlogPosts` など既存の読み取り経路の利用を検討し、トップの応答とコンテンツ更新の関係を設計する。
- 新着をトップ HTML に含めるなら、公開・非公開・削除時のキャッシュ更新対象に `/` を含めるか、同等の鮮度を保つ仕組みを用意する。現行 `blogHtmlCacheUrls` はブログの URL を対象にしている。
- 新しい Now や活動履歴は、現在専用の管理機能がある前提にしない。短文の管理場所・更新手順を決めてから導入する。
- Slides など外部情報を加える場合も、取得待ちで自己紹介や代表作を表示できなくしない。
- 音源・埋め込み・外部 API を導入する案では、その配信先と既存 CSP の整合も実装時に確認する。

### 操作とパフォーマンス

- 第一画面の氏名・紹介・主要リンクは、アニメーションや WebGL の完了を待たずに読めるようにする。
- 図・机・地図などの遊びがある案でも、同じ行き先へ通常のリンクで進めるようにする。
- キーボード操作、フォーカス表示、スマートフォンのタッチ、文字拡大、`prefers-reduced-motion` を含めて見比べる。
- 動きは意味のある一か所から試す。音は操作後に再生し、停止できるようにする。
- 画像には表示領域を確保し、読み込み時のずれを抑える。スマートフォンでは図を縮小するだけでなく、情報の並びを変える。
- 性能は既存の `perf/budgets.json` を基準に比較する。現行予算の例は LCP 2,500 ms、CLS 0.1、TBT 250 ms。新案が満たすかは実装後に測る。

## 9. 絞り込み方

### 最初に 3 枚だけ作るなら

1. **A02 / P02：設計図** — 専門性を最も具体的に見せる案。
2. **A03 / P03：コードと余白** — 技術と創作を同じ場所に置く案。
3. **A05 / P01：文字のポスター** — 少ない素材と情報で、印象を変える案。

同じ氏名・紹介・代表作 3 件を使い、デスクトップとスマートフォンの第一画面を並べて比較する。背景だけでなく、「何を最初に読むか」「どこへ進みたくなるか」の違いを見る。

### 比較する観点

| 観点 | 見たいこと |
| --- | --- |
| 人物像 | 短時間で、誰で・何を作っている人か説明できるか |
| 個人性 | 名前を別の人に変えたときにも成立してしまうほど汎用的ではないか |
| 次の行動 | 代表作・文章・自己紹介・連絡の行き先が分かるか |
| 素材との相性 | 今ある 3 作品と短い紹介だけでも成立するか |
| 続けやすさ | 更新しない月があっても、不自然にならないか |
| 増やしやすさ | 絵・音楽・記事が公開されたとき、自然に足せるか |
| モバイル | 小さな画面でも文字の順序と押しやすさが保たれるか |

採用後は既存の `home_featured_clicked` と `home_cta_clicked` の意味を維持し、必要なら案名・表示位置を属性に加える。記事欄を作る場合は記事へのクリックも比較対象にする。訪問が少ない期間は割合だけで勝敗を決めず、実数と実際に使ってもらった感想も見る。

### 段階的に進めるなら

1. **入口を作る**：名前・紹介・代表作・CTA と、選んだ方向性のモチーフを実装する。
2. **中身を足す**：事実に沿う代表作の図や解説を加え、公開記事があれば紹介する。
3. **個人の素材を足す**：本人の絵・写真・音が公開できたら、選んだ構成に加える。
4. **必要な分だけ動かす**：静止状態の完成度と性能を確かめてから、動きを足す。
